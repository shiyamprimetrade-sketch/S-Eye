# Stages 151–160: bounded processing and the Python request API

S-Eye observes software interfaces for S. This batch profiles and bounds that
observation path, reuses deterministic work, supports grouped memory operations,
and exposes a versioned Python client. It preserves Stage 84, previous recognition
paths, the default legacy tracker and all prior benchmarks. Main-S deployment,
semantic UI identity and version 1.0 readiness are not established.

## What the measurements show

- The loader preserves decoded pixels for RGB, grayscale, palette and alpha PNGs
  across all eight EXIF orientations, plus RGB/grayscale JPEGs with those rotations.
  The optimization removes one no-orientation copy; it does not reduce source
  resolution or change coordinate semantics. The generated timing probe is mixed:
  some cases are faster and others slower. No universal decode speedup is claimed.
- Reusing component selections produces identical ordered/schema-bound packets.
  Four generated selections make three component computations rather than six.
  Custom registered components must be pure for repeated-call equivalence.
- Three grouped queries match individual queries and exhaustive top-3 search at
  64, 512 and 2048 scalar records. Their authoritative inventory verification is
  shared once. A separate 256-record / 257-dimensional generated test also matches
  exhaustive search, but visits all 256 vectors per query: high-dimensional KD
  pruning has no measured distance-count advantage in this fixture. Verification
  still costs O(N); no large-scale or representative memory claim is made.
- Atomic insertion produces the same 64 observation IDs as individual inserts;
  invalid late records leave the batch unchanged, duplicates stay deduplicated,
  and rollback of an existing caller transaction removes its inserted batch.
  The mixed image test returns six successful observations and one malformed-image
  error in the original input order, with identical evidence to independent calls.
- The 12-request mixed/repeated packet-cache probe records four hits, eight misses
  and five evictions under a three-entry limit. Packets remain identical. File
  reads, hashing and image decoding still happen on every lookup; stored source
  bytes changing or a different schema causes a miss. This is not a decode cache.
- A 128-record SQLite snapshot reopens successfully with its derived index;
  the generated backup occupies 155648 bytes on this local SQLite build. Source
  bytes remain unchanged in the recovery test. File sizes/hashes can vary across
  SQLite versions and platforms. No automatic vacuum, deletion or overwrite runs.
- CPU/wall/Python allocation reports are observations of this process. CPU time
  includes its threads and excludes children/host utilization; the Linux RSS value
  is a lifetime high-water mark, not this workload's memory delta. Python tracing
  excludes most native allocations. Existing process tracing is never reset/stopped.

All data above are generated controls. Representative interface reliability,
real device workloads and actual Android ARM64 performance remain unvalidated.
The Stage 149 conservative tracker remains opt-in and still has worse aggregate
tracking metrics than the preserved legacy comparator. No tracking-accuracy claim
is changed by this performance batch.

## Stable Python API

The existing version-1 JSON request/response envelopes and command-line tools stay
compatible. `from seye.api import Client, Permissions, capabilities` is the public
Python entry point. `capabilities()` lists supported actions without accessing files
and explicitly reports `v1_release=false`. A Client snapshots the caller's explicit
grants, copies JSON input and rejects unsupported actions/nonfinite data/oversized
requests. Defaults grant no files, writes, memory, training or prerecorded video.

The default Client executes in a killable spawned worker with a 30-second deadline
(configurable up to 120 seconds). Use a normal main guard on Windows or other
spawn-based hosts:

```python
from pathlib import Path
from seye.api import Client, Permissions

if __name__ == '__main__':
    root = Path('screenshots').resolve()
    client = Client(Permissions(read_roots=(root,)))
    response = client.call('observe_interface', 'screen-1',
                           image=str(root / 'screen.png'),
                           region_proposals=True)
    print(response)
```

`isolated=False` is an explicit trusted-caller option for in-process integration;
it has no enforced execution deadline. Neither mode is an OS/native decoder
sandbox. A timeout does not undo writes that have already committed. Permission
and operational failures use the existing `success=false` envelope; malformed
Python/JSON API input raises a validation exception before execution. The main S
repository has not been changed or deployed by this batch.

| New action | Required fields | Grants and behavior |
| --- | --- | --- |
| `profile_interface` | `image`; optional existing observer options/templates/previous | Read roots for all sources; returns observation plus stage timings, refuses memory persistence |
| `observe_interface_batch` | `images`; optional `options` | Read roots for every path checked before work; ordered success/error items; no memory writes |
| `extract_feature_sets` | `image`, `selections` | Read root; one image, ordered feature packets with within-image component reuse |
| `extract_feature_batch` | `images`; optional `components` | Read roots; packet cache lives only for this request; each image is decoded afresh |
| `memory_packet_query_many` | `memory`, `packets`; optional query settings | Memory capability plus read root; one verified pinned read snapshot |
| `memory_storage` | `memory` | Memory capability plus read root; byte/page accounting without compaction |
| `memory_snapshot` | `memory`, `output`; optional `backup_timeout` | Memory capability, source read root and destination write root; exclusive verified backup |

Python and CLI share the same service implementation. The existing workflow flags
are `--allow-memory`, `--allow-training`, `--allow-video`, `--read-root`, and
`--write-root`. No request can supply new executable components, shell commands,
network access or UI action authorization.

## Bounds and limits

- Image loader: 32 MiB encoded bytes / 20 million pixels as hard global ceilings;
  callers can lower limits, not raise them. Interface paths cap each image at
  4 million pixels. Source pixels and orientation semantics are preserved.
- Image-observation batch: 1..32 sequential items, at most 64 MiB accepted encoded
  bytes and 8 million successfully decoded pixels. Failed bounded reads/decodes can
  consume additional work; item count and per-image bounds still apply. Feature
  batches have 1..32 images with per-image limits, rather than this aggregate budget.
- Feature selections: 1..32 groups, at most eight unique components per group,
  4096 values per packet and 32768 values across a reused-selection operation.
- Memory inserts: 1..128 records / 4 MiB canonical payload, one verified transaction.
  Grouped queries: 1..32 packets / 32768 feature values, at most 100 returned matches
  per query, with the existing 10000-record and million-index-value budgets.
- Packet LRU: at most 1024 entries / 16 MiB configured tracked entry estimates;
  defaults are 64 entries / 2 MiB. LRU container overhead, transient images and RSS
  are outside that estimate. Explicit clear resets entries and counters.
- Snapshot: at most 256 MiB, 10000 observations/history events, checked backup
  progress and a positive configured deadline up to 60 seconds. Output publication is exclusive
  and never overwrites. Abrupt process termination can leave a private temporary
  file; comprehensive crash/power-loss and native decoder isolation remain open.
- Client: 1 MiB canonical request / 16 MiB canonical response, up to 32 roots per
  grant category. Response checks occur after computation, not as a native memory
  ceiling. Scope counters/byte estimates are not process-RSS guarantees.
