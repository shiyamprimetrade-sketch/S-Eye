## Verified controls and their meaning

- All **297 local tests** pass, including historical regressions. All ten new
  integration experiments rerun with identical reports on this host. The final
  catalog contains **44 action contracts** and **six observation-tool specs**.
  Structural field checks are not proof that all actions succeeded on real data.
- Store/read/index/query roundtrips preserve the generated image's source digest.
  A wrong expected source is rejected before opening writable memory, so a failed
  source expectation does not create a memory database or modify its bytes.
- Controlled retrieval exercises `no_match`, `feature_candidate`, and `ambiguous`.
  The test uses one generated image and duplicate observations. It establishes
  cutoff/self-exclusion/tie behavior, not semantic recognition or calibrated trust.
- Count/box answers agree and identical-image changed-pixel fraction is zero.
  OCR, semantic button identity, code comprehension and action decisions return
  unsupported/none. A command-looking question is data and is never executed.
- Lifecycle controls exercise cancellation before startup and while a worker is
  running, deadline expiry, exit without a response and a wrong response ID.
  Spawned workers are reaped. Completed database/file writes are not rolled back.
- The installed five-step workflow executes from outside the checkout with default
  spawned workers and explicit grants: **observe → store → index → find → question**.
  The installed strict CLI answers a geometric question, and contract discovery
  works without granting operation files. This is a generated integration smoke,
  not registration in main S or representative autonomous computer use.

No new recognition-accuracy gain is claimed. The Stage 149 conservative tracker
remains opt-in with its worse aggregate metrics; the Stage 154 high-dimensional
query control still visits every vector. Representative application/device
validation, Android hardware performance and full native security remain open.

## Public entry points

`Client`, `Permissions`, and `capabilities` remain available from `seye.api`.
`Client(..., strict=True)` rejects unknown top-level action fields. Defaults stay
permissive about extra fields for legacy JSON callers, while the common envelope,
required fields, finite JSON values, depth and byte limits are checked. Direct
legacy `execute`/`handle` callers retain their established argument behavior.
Action-specific validation still applies after structural contract validation.

Machine-readable exports are `docs/contracts/request-v1.json` and
`docs/contracts/main-s-requirements-v1.json`. They use S-Eye's own documented
contract format; they are not an authenticated hardware/deployment attestation.
No request field selects an arbitrary Python module, shell command or callback.

| New action | Required inputs | Result and scope |
| --- | --- | --- |
| `memory_store_image` | `memory`, `image` | Explicit memory/write grants; source-bound record ID and hashes; optional components/expected source |
| `memory_get_observation` | `memory`, `observation_id` | Read-only memory observation plus verified content identities; stored data is not an instruction |
| `image_observe` | `image` | Captured source/pixel/observation hashes and geometric evidence; optional expected SHA-256 and bounded options |
| `memory_find` | `memory`, `image`, `maximum_distance` | Read-only indexed feature candidates, explicit ambiguity and self-source policy |
| `ask_observation` | `image`, `question` | Source-linked geometric answer or explicit unsupported/incomparable status |

`memory_find` supports optional `components`, `limit` (1..20), `include_self`,
`exclude_sources` and `expected_source_sha256`. Self-source/pixel matches are
excluded by default. A distance cutoff is required; it is a caller policy in
feature space, not a probability. Indexes must exist and be current. Reads never
silently rebuild them; `MemoryAdapter.build_index` is an explicit writable call.
A `feature_candidate` never proves the same physical/semantic object.

`ask_observation` supports exactly `count_proposed_regions`, `list_region_boxes`,
and `changed_pixel_fraction`. The last requires a `previous` image and abstains
on incompatible grids. Counts/boxes are unlabeled region hypotheses, not real
object counts or clickability. Unsupported questions provide no invented evidence.

## Typed adapters and explicit workflow

The memory adapter is read-only by default. Setting `writable=True` does not add
Client grants; explicit memory capability and write roots remain required.
`ToolsAdapter` offers observation only. Persistence uses the separate writable
memory adapter. Tool output is flagged as untrusted visual data and grants no
automatic action authority. Adapter configuration/preflight can raise validation
or permission exceptions; valid Client operations use version-1 result/error
responses. Screenshot labels/text cannot change the fixed dispatch map.

A normal spawn main guard is required on Windows and other spawn-based hosts:

```python
from pathlib import Path
from seye.api import Client, Permissions
from seye.integration.memory_adapter import MemoryAdapter
from seye.integration.session import EyeSession

if __name__ == '__main__':
    root = Path('workspace').resolve()
    client = Client(Permissions(read_roots=(root,), write_roots=(root,), memory=True),
                    strict=True)
    memory = MemoryAdapter(client, str(root / 'eye.sqlite3'), writable=True)
    session = EyeSession(client, 'example-session', memory)
    result = session.run(root / 'screen.png', persist=True)
    print(result)
```

Persistence is off by default. `persist=True` explicitly requests store and index
steps; retrieval happens only when `maximum_distance` is supplied. A later step
can fail after a write has committed; `successful_write_steps` remains in the
receipt. Expected source hashes bind each subsequent read to the first observed
capture. Workflow success means its requests completed, not that a semantic
question was answered or a UI action should be taken. Inspect each answer status.

Main S still needs to register the fixed tool specs, provide trusted captured
image paths, construct explicit grants, consume version-1 responses, and own its
separate decision/action layer. Those are connection requirements, not deployed
changes to another repository. Live camera acquisition remains disabled here.

## Cancellation, errors and CLI

`Client.request(request, cancel=threading.Event())` supports parent-side
cancellation with the default isolated worker. An already-set event prevents
worker startup. Inline mode refuses a cancellation token because it has no
killable worker. `Timeout`, `Cancelled`, `WorkerExited`, `InvalidResponse` and
`ResponseLimit` distinguish lifecycle failures. Ordinary permission/validation/
decoder/database errors keep their typed error envelopes.

The work deadline includes startup. Cleanup can add up to approximately 4.1
seconds for join/terminate/kill waits, plus scheduling overhead. It is not an
exact end-to-end real-time guarantee. Worker termination does not promise to kill
an entire native child-process tree. A timeout/cancellation is not a rollback;
committed side effects and abrupt-termination temporary files can remain.

```bash
seye-workflow --describe-contract
seye-workflow --request request.json --output response.json \
  --read-root /absolute/workspace --write-root /absolute/workspace --strict
```

Add `--allow-memory`, `--allow-video`, or `--allow-training` only for the explicitly
requested capabilities. Existing CLI names and successful request modes are
preserved. The request file is limited to 1 MiB and decoded as UTF-8 (UTF-8 BOM is
accepted). Duplicate keys/nonfinite values/excessive depth are refused. Response
JSON is capped at 16 MiB. Strict mode rejects unknown action fields. Exit codes:
0 for success/discovery, 1 for an operation error, 2 for invalid CLI/input setup.
Keyboard interruption during bounded work produces a cancellation response when
normal parent cleanup can run; forced termination cannot guarantee a receipt.

## Boundary and release limits

Grants are normalized/frozen, capability booleans are strict, and operation paths
must be regular files when present. Traversal, escaping symlinks, ordinary source
replacement and replacement of a granted root directory are tested. Pre/post
metadata checks do not authenticate a file or eliminate every race between checks
and OS open calls. No native OS sandbox, total decoder RSS ceiling, hostile
filesystem immunity, live camera or physical-device validation is certified.
Existing per-image/feature/memory/video limits continue to apply.

Source preservation audit, installed CLI/Python/session smokes and development
wheel build pass. Exact-head Linux/Windows CI is recorded in the status/ledger.
